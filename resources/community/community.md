# Community Accessibility Resources

This guide supports the [Community Phase](https://open-source-accessibility.github.io/Open-Source-Accessibility-Framework/community) of the [Open Source Accessibility Framework](https://open-source-accessibility.github.io/Open-Source-Accessibility-Framework/). Use it to find learning materials, community-engagement guidance, participation opportunities, and examples that can help you complete the phase.

The resources are examples, not framework requirements or endorsements. Choose resources that fit your project's users, technology, location, language, and contribution model.

## Community principles

Apply these principles across every Community Phase action:

- **Treat accessibility as the baseline and usability as the goal.** Technical conformance is essential, but people must also be able to participate successfully, efficiently, and with dignity.
- **Include disabled people in decisions that affect them.** Lived experience and accessibility expertise complement standards and technical testing.
- **Provide multiple ways to participate.** Offer synchronous and asynchronous options when practical.
- **Respect privacy, autonomy, and labor.** Request consent before sharing personal information or recognizing a contributor, and do not assume substantial accessibility work will be unpaid.
- **Avoid tokenism.** No individual represents an entire disability community; seek perspectives that reflect the project's users.
- **Close the feedback loop.** Communicate decisions, outcomes, unresolved barriers, workarounds, and next steps.
- **Create paths to leadership.** Enable accessibility contributors to become reviewers, maintainers, advisors, and project leaders.

## Resources by Community Phase action

### Responding to accessibility reports

Use these examples to create respectful reporting and response practices:

- [Accessibility Toolkit `ACCESSIBILITY.md`](https://github.com/open-source-accessibility/accessibility-toolkit/blob/main/ACCESSIBILITY.md) provides an example accessibility statement and response guidance.
- [GitHub issue and pull request template guidance](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests) explains how to collect useful information consistently.
- [GitHub Accessibility Documentation](https://accessibility.github.com/documentation) provides guidance for people using GitHub with assistive technologies.

### Communicating progress

Use public channels that your community already follows, such as issues, release notes, discussions, roadmaps, newsletters, or meeting updates.

- [Open Source Accessibility community discussions](https://github.com/orgs/open-source-accessibility/discussions) provides examples of public accessibility conversations.
- [Open Source Guides: Best Practices for Maintainers](https://opensource.guide/best-practices/) covers transparent communication and sustainable project practices.
- [CHAOSS](https://chaoss.community/) provides community-health metrics that can help projects measure and communicate progress.

### Learning and participation

These resources can help contributors learn accessibility and develop open source participation skills:

- [W3C Web Accessibility Initiative](https://www.w3.org/WAI/) provides authoritative accessibility standards, tutorials, and planning guidance.
- [The A11Y Project](https://www.a11yproject.com/) offers practical, community-created accessibility education.
- [Community Access](https://community-access.org/) provides accessibility-focused learning and open source participation resources.
- [GIT Going with GitHub](https://community-access.org/git-going-with-github/) offers accessible instruction for Git, GitHub, issues, pull requests, reviews, and contribution workflows.
- [GIT Going with GitHub Learning Room](https://community-access.org/git-going-with-github/learning-room/) provides a space to learn and practice contribution skills.
- [Open Source Guides: Contributing to Open Source](https://opensource.guide/how-to-contribute/) introduces common open source contribution practices.

### Accessible community practices

Use these resources to make contributor guidance, communication, events, and governance more accessible:

- [W3C: Accessibility, Usability, and Inclusion](https://www.w3.org/WAI/fundamentals/accessibility-usability-inclusion/) explains how these concepts relate.
- [W3C: How People with Disabilities Use the Web](https://www.w3.org/WAI/people-use-web/) describes how barriers affect people with different disabilities.
- [W3C: Involving Users in Web Projects](https://www.w3.org/WAI/planning/involving-users/) explains how to include disabled users throughout a project.
- [GitHub: Building Welcoming Communities](https://opensource.guide/building-community/) covers healthy and inclusive community practices.
- [GitHub code of conduct guidance](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/adding-a-code-of-conduct-to-your-project) explains how to add and enforce community standards.
- [CHAOSS Project Access](https://www.chaoss.community/kb/metric-project-access/) helps projects assess whether contributors can find and access participation opportunities.
- [CHAOSS Event Accessibility](https://chaoss.community/kb/metric-event-accessibility/) and [Chat Platform Inclusivity](https://www.chaoss.community/kb/metric-chat-platform-inclusivity/) provide questions for evaluating events and communication tools.

When reviewing community tools and workflows, consider keyboard access, screen reader support, captions, transcripts, accessible documents and chat, magnification, reflow, and clear interaction patterns.

### Sharing resources and solutions

Share templates, tests, design patterns, documentation, examples, and lessons learned so other projects can build on your work.

- [Open Source Accessibility community show-and-tell](https://github.com/orgs/open-source-accessibility/discussions/new?category=show-and-tell) provides a place to share accessibility work.
- [A11yhood](https://a11yhood.org/) supports the discovery and sharing of open source accessibility technology.
- [UW CREATE's A11yhood project page](https://create.uw.edu/initiatives/rerc-home/a11yhood-repository/) describes A11yhood's goals for tutorials, reviews, technical assistance, and technology sharing.
- [Accessibility Toolkit](https://github.com/open-source-accessibility/accessibility-toolkit) provides reusable accessibility templates and examples.
- [Grassroots Open Assistive Tech](https://www.openassistivetech.org/) shares open assistive-technology designs and community knowledge.

Include enough context for others to reuse a resource: the problem it solves, prerequisites, instructions, limitations, known tradeoffs, and situations where it may not apply.

### Recognition and community health

Recognition shows that accessibility work is valuable project work, whether it involves code, testing, documentation, research, design feedback, mentoring, translation, or community support.

- [Open Source Accessibility community shoutout](https://github.com/orgs/open-source-accessibility/discussions/new?category=shoutout) provides a place to recognize accessibility contributions.
- [CHAOSS Contribution Attribution](https://www.chaoss.community/kb/metric-contribution-attribution/) helps projects evaluate how contributions receive credit.
- [CHAOSS Types of Contributions](https://www.chaoss.community/kb/metric-types-of-contributions/) helps projects recognize work beyond code.
- [GitHub: Leadership and Governance](https://opensource.guide/leadership-and-governance/) discusses pathways to responsibility and leadership.

Ask contributors whether and how they want to be recognized. Never disclose a person's disability, diagnosis, assistive technology use, or other personal information without permission.

## Choosing and maintaining resources

When adding resources to project guidance:

1. Prefer primary sources for standards and platform behavior.
2. Include disability-led or disability-partnered communities for lived-experience and participation guidance.
3. Explain how each resource helps instead of publishing an undifferentiated link list.
4. Include multiple perspectives rather than treating one organization or person as representative of everyone.
5. Review links and descriptions periodically as standards, tools, and communities evolve.
